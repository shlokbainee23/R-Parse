# R AST & Program Representation Architectural Comparison

This document provides a comparative analysis of abstract syntax tree (AST) and concrete syntax tree (CST) representations across the R language ecosystem.

---

## 1. Overview of Representational Paradigms

| Representation | Used By | Tree Type | Source Fidelity | Comments Preserved | Memory Overhead | Traversal Mechanism |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **Native S-Expression (SEXP / pairlist)** | GNU R core, `CodeDepends`, `targets`, `rpy2` | AST | Moderate (lossy) | **No** | Low (Native C structs) | Recursive CAR/CDR or R `[[i]]` indexing |
| **Flat Parse Table (`getParseData`)** | Base R `utils`, internal compiler | Tabular CST | High | **Yes** (parent = -1) | High (Data frame of vectors) | Vector filtering / row index lookup |
| **XML DOM Document** | `xmlparsedata`, `lintr`, `languageserver` | XML CST | High | **Yes** (via `fix_comments`) | Very High (libxml2 C DOM + R wrappers) | XPath 1.0 queries |
| **Tree-sitter Concrete Syntax Tree** | `tree-sitter-r`, `flowR` (backend) | Lossless CST | Complete | **Yes** (as explicit comment nodes) | Moderate (Packed C node arena) | Tree-sitter C Cursor API / Tree queries |
| **Normalized Semantic AST** | `flowR` (core IR) | Normalized AST | High | **Yes** (attached trivia) | Moderate (V8 JS object graph) | Strongly-typed Visitor / Catamorphism |

## 2. Detailed Technical Comparison

### 2.1 GNU R Native S-Expressions (SEXP)
- **Data Structure:** Recursive singly-linked pairlists (`LISTSXP`, `LANGSXP`) and vectors (`VECSXP`).
  - Head of list is the function/operator (`CAR`), tail is arguments (`CDR`).
  - Example: `x + 1` is represented as a call object where `CAR` is `+`, `CADR` is `x`, and `CADDR` is `1`.
- **Strengths:** 
  - Zero conversion overhead when executing inside the R runtime.
  - Native support for R metaprogramming (`substitute()`, `quote()`, `eval()`).
- **Critical Limitations:**
  - **Loss of Source Trivia:** Comments are completely stripped during parsing unless `keep.source=TRUE` attaches an auxiliary `srcref` attribute.
  - **Parentheses Flattening:** Redundant parentheses `((x))` are often lost or normalized away.
  - **Mutable In-Place Risk:** S-expressions in R are historically subject to complex copy-on-modify semantics; careless C-level manipulation can corrupt active runtime frames.

### 2.2 Flat Parse Table (`utils::getParseData()`)
- **Data Structure:** An R `data.frame` with columns:
  - `line1`, `col1`, `line2`, `col2`: 1-based source coordinates.
  - `id`: Unique integer node identifier.
  - `parent`: Integer ID of the parent expression node (or `0` for root, `-id` for comments).
  - `token`: String name of the grammar token (e.g. `SYMBOL`, `NUM_CONST`, `expr`).
  - `terminal`: Logical indicating whether the node is a leaf token.
  - `text`: Exact source text slice.
- **Strengths:**
  - Retains 100% of tokens, whitespace boundaries, and comments.
  - Standard data frame interface allows filtering via standard R operations (`subset(pd, token == "SYMBOL")`).
- **Critical Limitations:**
  - **Inefficient Tree Traversal:** Walking up or down the hierarchy requires relational joins or recursive row filtering (`pd[pd$parent == id, ]`), which is asymptotically slow ($O(N^2)$ for deep trees without index caching).
  - **No Typed Node Abstractions:** All nodes are generic rows with string token tags.

### 2.3 XML DOM Representation (`xmlparsedata`)
- **Data Structure:** Hierarchical XML string generated by string concatenation in R (`package.R` line 60), parsed into a C DOM via `xml2::read_xml()`.
  - Non-terminals: `<exprline ...><expr>...</expr></exprline>`
  - Terminals: `<SYMBOL>x</SYMBOL>`, `<OP-PLUS>+</OP-PLUS>`, `<NUM_CONST>1</NUM_CONST>`
- **Strengths:**
  - Enables standard **XPath 1.0** queries (`//SYMBOL_FUNCTION_CALL[text() = 'filter']`).
  - Allows declarative rule authoring in linters (`lintr` has 118 linters built on this).
- **Critical Limitations:**
  - **Extreme Serialization Overhead:** Stringifying parse tables into XML and re-parsing into `libxml2` creates massive GC pressure and latency. In benchmarks, generating and querying the XML DOM is over 50x slower than traversing native trees.
  - **XPath 1.0 Expressiveness Limit:** XPath 1.0 lacks regular expression matching, transitive closure functions, and complex graph reachability checks.

### 2.4 Tree-sitter Concrete Syntax Tree (`tree-sitter-r`)
- **Data Structure:** Compact C node array managed by the Tree-sitter runtime.
  - Every node is either a named rule (`identifier`, `binary_operator`, `call`) or an anonymous token (`+`, `(`, `<-`).
  - Field names provide direct O(1) child access (`call.function`, `call.arguments`).
- **Strengths:**
  - **Fault Tolerance:** Can parse incomplete and syntactically malformed code, generating `ERROR` nodes while maintaining structure for surrounding code.
  - **Incremental Reparsing:** Modifying a single character only re-parses the affected branch in microseconds.
  - **Zero R Dependency:** 100% standalone C parser.
- **Critical Limitations:**
  - **CST Verbosity:** Retains every paren, comma, and newline; higher-level semantic analyzers must manually filter out punctuation.
  - **No Semantic Normalization:** Does not unify assignment variants (`<-`, `=`, `->`).

### 2.5 Normalized Semantic AST (`flowR`)
- **Data Structure:** Strongly-typed TypeScript class hierarchy (`src/r-bridge/lang-4.x/ast/model/`).
  - Unifies syntax into canonical nodes: `Identifier`, `Literal`, `BinaryOp`, `Call`, `Pipeline`, `FunctionDef`, `ControlFlowBlock`.
  - Stores rich node metadata: exact source range, parent pointer, attached comments, enclosing lexical scope.
- **Strengths:**
  - Canonicalization simplifies static analysis passes: an analysis rule checking assignments only inspects `AssignmentNode` without needing branches for `<-`, `=`, `->`, or `assign()`.
  - Directly bridges into Control Flow Graph (CFG) and Dataflow Graph generation.
- **Critical Limitations:**
  - **Language Ecosystem Lock-in:** Tied to TypeScript / Node.js runtime environment.
  - **Maintenance Overhead:** Any R grammar update requires updating both the parser bridge and the TypeScript AST class definitions.

## 3. Comparative Node Mapping Example

Consider the canonical R expression:
```r
res <- compute(data = df, scale = TRUE)
```

### Representation Comparison Across Systems:

#### 1. Flat Parse Table (`getParseData`):
```text
line1 col1 line2 col2 id parent terminal token text
    1    1     1    3  1      3     TRUE SYMBOL res
    1    5     1    6  2      3     TRUE LEFT_ASSIGN <-
    1    8     1   14  4      6     TRUE SYMBOL_FUNCTION_CALL compute
    1   15     1   15  5     15     TRUE '(' (
    1   16     1   19  7      9     TRUE SYMBOL_SUB data
    1   21     1   21  8      9     TRUE EQ_SUB =
    1   23     1   24 10     11     TRUE SYMBOL df
...
```

#### 2. XML DOM (`xmlparsedata`):
```xml
<exprlist>
  <expr line1="1" col1="1" line2="1" col2="39">
    <expr line1="1" col1="1" line2="1" col2="3">
      <SYMBOL>res</SYMBOL>
    </expr>
    <LEFT_ASSIGN>&lt;-</LEFT_ASSIGN>
    <expr line1="1" col1="8" line2="1" col2="39">
      <SYMBOL_FUNCTION_CALL>compute</SYMBOL_FUNCTION_CALL>
      <OP-LEFT-PAREN>(</OP-LEFT-PAREN>
      <SYMBOL_SUB>data</SYMBOL_SUB>
      <EQ_SUB>=</EQ_SUB>
      <expr line1="1" col1="23" line2="1" col2="24">
        <SYMBOL>df</SYMBOL>
      </expr>
      <OP-COMMA>,</OP-COMMA>
      <SYMBOL_SUB>scale</SYMBOL_SUB>
      <EQ_SUB>=</EQ_SUB>
      <expr line1="1" col1="35" line2="1" col2="38">
        <NUM_CONST>TRUE</NUM_CONST>
      </expr>
      <OP-RIGHT-PAREN>)</OP-RIGHT-PAREN>
    </expr>
  </expr>
</exprlist>
```

#### 3. Tree-sitter CST (`tree-sitter-r`):
```text
(program
  (binary_operator
    lhs: (identifier) ; "res"
    operator: "<-"
    rhs: (call
      function: (identifier) ; "compute"
      arguments: (arguments
        (argument
          name: (identifier) ; "data"
          value: (identifier)) ; "df"
        (argument
          name: (identifier) ; "scale"
          value: (true)))))) ; "TRUE"
```

#### 4. Normalized AST (`flowR`):
```text
AssignmentNode {
  target: IdentifierNode { name: "res" },
  value: CallNode {
    callee: IdentifierNode { name: "compute" },
    arguments: [
      NamedArgument { name: "data", value: IdentifierNode { name: "df" } },
      NamedArgument { name: "scale", value: BooleanLiteralNode { value: true } }
    ]
  },
  operator: AssignmentOperator.LeftArrow
}
```

## 4. Key Takeaways for R-PARSE

1. **Raw S-expressions are inadequate** for static tooling because they drop comments, strip parentheses, and lose byte-precise source spans.
2. **XML DOM is an architectural dead-end** due to high serialization overhead and query performance limits, despite its popularity in `lintr`.
3. **Lossless CST + Normalized Semantic AST two-layer architecture** (as demonstrated conceptually by Tree-sitter + flowR) is the only architecture capable of simultaneously supporting:
   - Incremental, fault-tolerant syntax highlighting and formatting.
   - High-speed, strongly-typed semantic passes, CFG construction, and SSA dataflow analysis.
